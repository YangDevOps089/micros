# Домашнее задание к занятию «Микросервисы: подход»

## Задача 1: Обеспечить разработку

| Требование | GitLab | GitHub + Actions | Jenkins | TeamCity | Bitbucket |
|---|---|---|---|---|---|
| Облачная система | да | да | нет | да | да |
| Встроенный Git | да | да | нет | нет | да |
| Сборка по событию из VCS | да | да | да, webhook | да | да |
| Сборка по кнопке с параметрами | да | да | да | да | да |
| Настройки для каждой сборки | да | да | да | да | да |
| Шаблоны конфигураций | да, include, extends | да, reusable workflows | да, shared libraries | да | частично |
| Хранение секретов | да, masked/protected, Vault | да | да, Credentials | да | да |
| Несколько конфигураций из одного репо | да | да | да | да | да |
| Кастомные шаги | да | да | да | да | да |
| Свои докер-образы | да, есть свой registry | да | да | да | да |
| Агенты на своих серверах | да, GitLab Runner | да | да | да | да |
| Параллельные сборки и тесты | да, parallel, matrix | да, matrix | да | да | да |
| Доступность в РФ | да, есть Managed GitLab в Yandex Cloud | бесплатный тариф, оплата затруднена | да | вендор ушёл | вендор ушёл |

**Выбор: GitLab.** Jenkins не облачный и требует отдельного Git-хостинга. У TeamCity и Bitbucket вендоры ушли из РФ. GitHub подходит по функциям, но у GitLab в одном продукте есть код, CI/CD, registry и окружения, и его можно взять управляемым сервисом в Yandex Cloud.

Как устроено:
- каждый сервис в своём репозитории в группе `microservices`, общие права и переменные задаются на уровне группы;
- общие шаблоны сборки лежат в репозитории `ci-templates` и подключаются в сервисах через `include` и `extends`;
- пайплайн запускается на push, MR и тег, вручную через Run pipeline с переменными; через `rules` задаётся, что выполнять в каждом случае, для нескольких конфигураций в одном репо используются parent-child pipelines;
- секреты хранятся в masked и protected переменных, при необходимости в Vault;
- job'ы выполняются в своих образах из GitLab Container Registry;
- GitLab Runner стоит на своих серверах или в Kubernetes, количество параллельных job'ов задаётся `concurrent`, тесты разбиваются через `parallel: N`.

## Задача 2: Логи

| Требование | Loki + Grafana | Elasticsearch + Kibana | OpenSearch + Dashboards | Graylog |
|---|---|---|---|---|
| Сбор со всех хостов | агент на каждом хосте (Fluent Bit, Alloy, Vector) | Filebeat, Fluent Bit | Fluent Bit, Vector | Fluent Bit, GELF |
| Сбор из stdout | да, из логов контейнеров | да | да | да |
| Гарантированная доставка | буфер на диске у агента, WAL и репликация в Loki | буфер у агента, реплики в кластере | буфер у агента, реплики в кластере | журнал на диске |
| Поиск и фильтрация | LogQL, индекс только по меткам | полнотекстовый | полнотекстовый | полнотекстовый |
| UI с доступом для разработчиков | Grafana, роли и команды | Kibana, роли | Dashboards, роли | роли |
| Ссылка на сохранённый поиск | да, share link и панели | да, saved search | да, saved search | да, saved search |
| Требования к ресурсам | низкие, данные в S3 | высокие | высокие | высокие (OpenSearch + MongoDB) |
| Доступность в РФ | да | загрузка с elastic.co из РФ заблокирована | да | да |

**Выбор: Loki + Grafana, агент Fluent Bit.** Все варианты закрывают требования, но Loki не индексирует текст логов, только метки, поэтому требует в разы меньше ресурсов и хранит данные в дешёвом S3. Grafana будет общим интерфейсом и для логов, и для мониторинга из задачи 3. Если понадобится полнотекстовый поиск по большим объёмам, альтернатива OpenSearch.

Как устроено:
- приложения пишут логи в stdout, ничего больше от них не требуется;
- Fluent Bit стоит на каждом хосте (в Kubernetes как DaemonSet), читает логи контейнеров и добавляет метки: сервис, хост, окружение;
- гарантированная доставка: Fluent Bit буферизует логи на диск и повторяет отправку, пока Loki не подтвердит приём; в Loki включены WAL и репликация (replication_factor 3), данные хранятся в Object Storage;
- поиск через LogQL, например `{service="orders"} |= "error" | json | status >= 500`;
- разработчикам выдаётся доступ в Grafana через команды и права на папки;
- ссылка на поиск делается через Share в Explore или сохраняется как панель на дашборде.

## Задача 3: Мониторинг

| Требование | Prometheus + Grafana | Zabbix | VictoriaMetrics + Grafana | InfluxDB + Telegraf + Grafana |
|---|---|---|---|---|
| Сбор со всех хостов | node_exporter | Zabbix agent | node_exporter, vmagent | Telegraf |
| CPU, RAM, HDD, Network хоста | да | да | да | да |
| Ресурсы каждого сервиса | cAdvisor, kubelet | частично, шаблон Docker | cAdvisor, kubelet | плагин docker |
| Метрики сервиса | да, /metrics и клиентские библиотеки | неудобно, через HTTP agent | да, совместим с Prometheus | да |
| Запросы и агрегация | PromQL | слабо | MetricsQL (совместим с PromQL) | InfluxQL, Flux |
| Настраиваемые дашборды | Grafana | да, но беднее | Grafana | Grafana |
| Service discovery в Kubernetes | да | нет | да | частично |

**Выбор: Prometheus + Grafana.** Это стандарт для микросервисов: сервисы сами отдают метрики в формате Prometheus, есть готовые экспортеры почти под всё и автообнаружение сервисов в Kubernetes. Zabbix хорош для классической инфраструктуры, но плохо работает с динамическими контейнерами и метриками приложений. VictoriaMetrics можно добавить позже как долговременное хранилище, если Prometheus перестанет справляться.

Как устроено:
- node_exporter на каждом хосте собирает CPU, RAM, диски и сеть;
- cAdvisor (в Kubernetes встроен в kubelet) собирает потребление ресурсов по каждому контейнеру;
- каждый сервис отдаёт свои метрики на `/metrics` через клиентскую библиотеку;
- Prometheus сам находит цели через service discovery и опрашивает их;
- Alertmanager рассылает алерты;
- в Grafana делаются запросы на PromQL и настраиваются дашборды, там же логи из Loki, поэтому метрики и логи смотрятся в одном месте.
