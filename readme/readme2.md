# API Gateway

## Требования

- маршрутизация запросов к нужному сервису на основе конфигурации;
- проверка аутентификационной информации в запросах;
- терминация HTTPS.

## Сравнение решений

Для сравнения взял решения, которые чаще всего встречаются в self-hosted инсталляциях. 

| | Nginx (OSS) | Traefik (OSS) | Kong Gateway (OSS) | Apache APISIX | Envoy / Envoy Gateway | KrakenD (CE) |
|---|---|---|---|---|---|---|

## Что выбрал и почему

Все три требования из коробки закрывают Kong, APISIX, Envoy и KrakenD. Nginx OSS и Traefik OSS проверяют JWT только через отдельный сервис аутентификации (auth_request / ForwardAuth), то есть его придётся писать и поддерживать отдельно. Поэтому их отбросил.

Из оставшихся выбрал **Kong Gateway в режиме DB-less**:

1. Маршрутизация. Маршруты описываются в YAML (services → routes → upstreams) и хранятся в Git вместе с остальной инфраструктурой. Конфиг применяется через deck в CI/CD. В DB-less режиме база данных не нужна, поэтому дополнительных компонентов нет.
2. Аутентификация. Готовые плагины key-auth, jwt, basic-auth, oauth2, плюс acl для ограничения доступа к маршрутам по группам потребителей. Плагины включаются на нужных маршрутах, в коде сервисов ничего менять не надо. После проверки Kong передаёт в сервис заголовки с данными потребителя.
3. HTTPS. Сертификаты хранятся в конфиге Kong, поддерживается SNI. Внутри кластера трафик к сервисам идёт по HTTP или mTLS. Для автоматического выпуска сертификатов в Kubernetes можно использовать cert-manager.
4. Rate limiting, CORS, логи и метрики Prometheus тоже есть плагинами, при эксплуатации они понадобятся.
5. Самое распространённое open source решение такого класса, много документации и готовых примеров. Есть Ingress Controller с поддержкой Gateway API.

Почему не остальные:
1. APISIX по функциям почти такой же, но требует etcd. Это ещё один кластер, который нужно поддерживать.
2. Envoy самый производительный и гибкий, но сложный в настройке. Имеет смысл, если в будущем планируется service mesh (Istio). Тогда гейтвей и межсервисный трафик будут на одной технологии.
3. KrakenD простой и быстрый, но слабее по матчингу маршрутов и набору функций аутентификации.


# Задача 2: Брокер сообщений

## Сравнение решений

| | RabbitMQ | Apache Kafka | NATS JetStream | Apache Pulsar | Redis Streams |
|---|---|---|---|---|---|
| Кластеризация | да, quorum queues (Raft) | да, репликация партиций (KRaft) | да, Raft | да, брокеры + BookKeeper | да, но репликация асинхронная |
| Хранение на диске при доставке | да | да | да | да | в основном в памяти, на диск через RDB/AOF |
| Скорость | высокая | очень высокая | очень высокая | очень высокая | очень высокая |
| Форматы сообщений | любые байты, content-type; AMQP, MQTT, STOMP | любые байты, Schema Registry (отдельно) | любые байты; MQTT, WebSocket | любые байты, встроенный Schema Registry | пары ключ/значение |
| Разделение прав доступа | vhost + права read/write/configure на очереди | ACL на топики | accounts, права на subjects | tenants, namespaces, права на топики | ACL на ключи |
| Простота эксплуатации | высокая | средняя | высокая | низкая (3 компонента) | высокая |

## Выбор: RabbitMQ

Redis Streams отпадает, потому что сообщения хранятся в памяти и при сбое возможна потеря. Pulsar отпадает по простоте эксплуатации: брокеры, BookKeeper и ZooKeeper, то есть три системы вместо одной.

Из оставшихся выбрал RabbitMQ, потому что он закрывает все требования без оговорок:

- кластеризация: quorum queues реплицируются по Raft, кластер из 3 узлов переживает потерю одного;
- сообщения пишутся на диск и удаляются только после подтверждения (ack) от потребителя;
- скорости хватает для взаимодействия микросервисов, для больших потоков есть RabbitMQ Streams;
- тело сообщения произвольное (JSON, Protobuf, Avro), поддерживается несколько протоколов;
- права разделяются через vhost и права пользователя на конкретные очереди и exchange;
- кластер состоит только из узлов RabbitMQ, есть веб-консоль, метрики Prometheus и оператор для Kubernetes.

Kafka быстрее, но сложнее в эксплуатации (партиции, retention, ребалансировка). Её стоит брать, если нужны сотни тысяч сообщений в секунду или хранение и повторное чтение событий. NATS JetStream по требованиям подходит, но у него меньше сообщество и опыт эксплуатации, чем у RabbitMQ.
